# Разработка на Битрикс24

Используй навык, когда пользователь делает приложение для Битрикс24: вкладку в карточке CRM, пункт левого меню, виджет или любой код, читающий данные портала.

## Сначала выбери архитектуру

Это первое решение, и оно определяет, можно ли вообще пользоваться официальным BX24 JS SDK. Ошибка здесь стоит переписывания слоя данных, а не правки пары строк.

| | Локальное приложение | Приложение платформы (VibeCode) |
|---|---|---|
| Обработчик | твой URL | жёстко задан платформой |
| BX24 JS SDK | работает | **не работает** |
| Свой бекенд | не нужен | обязателен (BFF) |
| Установка | вручную в UI портала | полностью скриптуется |

Спроси пользователя до начала работы. Типичный конфликт: в ТЗ написано «официальный BX24 JS SDK» и «без бекенда», а деплой планируется на платформу — это несовместимо, и узнать об этом лучше до кода.

## Приложение платформы

Обработчик всегда платформенный, сменить его нельзя. Он принимает placement от Битрикс24 и редиректит iframe на `appUrl`, донося только `placement`, `member_id`, `placement_options`. `DOMAIN`, `AUTH_ID` и `APP_SID` теряются.

Следствия:

- `BX24.init()` не сделает handshake, `BX24.placement.info()` вернёт `{placement:null, options:null}`. SDK не использовать.
- ID карточки бери из query: `JSON.parse(params.get('placement_options')).ID`.
- Данные читает бекенд: Gateway подставляет `X-Vibe-Authorization`, приложение ходит в API с ключом приложения. Токен в браузер не отдавать.
- Для видимости в портале нужен **bind**, а не **publish**. Подробности — в `references/vibecode-deploy.md`.

## Локальное приложение

Регистрируется в портале: **Приложения → Разработчикам → Другое → Локальное приложение**, галочка «Использует только API» снята. Битрикс24 сам передаёт `DOMAIN`/`AUTH_ID`/`APP_SID`, поэтому SDK работает штатно и бекенд не нужен.

- `BX24.callMethod` проксирует REST через родительский фрейм — токены не покидают портал.
- Встройки привязывает сам фронтенд на странице установки: `placement.bind` для каждого места, затем `BX24.installFinish()`. Перед `bind` делай `unbind` — тогда переустановка идемпотентна.
- Обработчик открывается методом **POST**, а не GET. Статика, отвечающая только на GET, вернёт 405 — сервер должен отдавать страницу на оба метода.
- Не выставляй `X-Frame-Options`: страницу грузит iframe портала.

## Данные портала

- Семантика сделки — `stageSemanticId`: `S` выиграна, `F` проиграна, `P` в работе. Не опирайся на названия стадий: они у каждого портала свои.
- Магические числа (`status` задач, приоритеты) не хардкодь — расшифровку отдаёт `fields` соответствующей сущности.
- Названия сделок, контактов и компаний — недоверенные данные из CRM. Экранируй перед вставкой в разметку.

### Валюты

Справочник валют портала отдаёт курс как `AMOUNT` за `AMOUNT_CNT` единиц, выраженный в **базовой валюте портала**.

```text
курс(валюта)    = AMOUNT / AMOUNT_CNT
сумма_в_базовой = сумма * курс(валюта сделки)
сумма_в_целевой = сумма_в_базовой / курс(целевая валюта)
```

Копи суммы в базовой валюте и конвертируй только на выводе — иначе сделки в разных валютах сложатся неверно. Не считай, что базовая валюта — рубль: формула выше от этого не зависит. Сделку в валюте, которой нет в справочнике, пересчитать нельзя — не молчи об этом, показывай счётчик неучтённых.

## Проверка

Дашборд внутри портала снаружи не открыть: сессия появляется только при настоящем открытии встройки. Поэтому:

1. Считай эталон по данным портала через REST заранее и сверь с тем, что покажет интерфейс.
2. Логику проверяй в браузере на стенде с мок-версией источника данных, на реальных данных портала.
3. Прогоняй состояния: loading, error, empty, нет курса, валюта без курса, открыто вне карточки, название с HTML внутри.
4. Финальный прогон в живой карточке — за пользователем, честно скажи, что сам этого не видел.

## Стиль текста

- В русскоязычных пояснениях, инструкциях и документации используй букву `ё` с точками там, где она нужна; не заменяй её на `е`.
- В пояснениях и примерах не злоупотребляй списками: максимум три пункта по умолчанию. Более длинные списки допустимы для обязательных правил, состояний, проверок или API-параметров, где сокращение сломает смысл.
- Пиши рекомендации активным залогом, когда понятно, кто рекомендует или выполняет действие. Пример: не "В Bitrix Framework собственные сообщения рекомендуется создавать на основе класса", а "В Bitrix Framework мы рекомендуем создавать собственные сообщения на основе класса".

## Правила разработки

- Перед реализацией соблюдай 5 правил профессионального вайб-кодинга: строгая типизация, обязательный линтер, тесты для каждого изменения, измерение покрытия и валидация входных данных с контролем зависимостей.
- Для Битрикс24-приложений особенно проверяй границы данных: query-параметры placement, ответы REST, CRM-названия, валюты, стадии и любые значения, которые приходят из портала.
- Если стек или платформа мешают выполнить одно из правил, явно назови компромисс и добавь ближайшую защиту: схему, runtime-валидатор, smoke-test, линтер-конфиг или отдельную проверку.
