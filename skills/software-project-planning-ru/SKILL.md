# Планирование разработки

Используй навык, когда пользователь хочет спланировать программный проект, MVP, интеграцию, библиотеку или технический прототип.

## Порядок работы

1. Определи цель продукта, пользователей, окружение, ограничения и интеграции.
2. Раздели работу на проверяемые этапы с результатом каждого этапа.
3. Для каждого этапа укажи файлы или модули, проверки, тесты и критерии готовности.
4. Отдельно отметь риски: неизвестные API, безопасность, данные, миграции, производительность.
5. Не начинай реализацию следующего этапа, если пользователь просит пошаговый режим с подтверждением.
6. В конце дай минимальный набор команд для проверки проекта.

## Инженерные правила

- Выбирай строго типизированный язык. Если это невозможно, добавляй явные схемы или валидаторы типов на границах системы.
- Всегда включай в проект линтер и его запуск в обязательные проверки.
- Для каждого изменения кода требуй создать или обновить тесты и запустить все относящиеся к изменению тесты. Если реализацию выполняет ИИ, явно добавляй это требование в каждый промпт на изменение кода.
- Планируй измерение тестового покрытия. Устанавливай порог не ниже 70%, целевой уровень — 80%; для критичной логики повышай порог с учётом риска.
- Валидируй все входные и внешние данные до использования.
- Минимизируй число фреймворков и зависимостей.
- Планируй регулярное обновление зависимостей, проверку устаревших пакетов и аудит известных уязвимостей.
- Не закладывай хранение секретов в коде.
- Покрывай тестами поведение, а не только happy path.
- В русскоязычных планах, пояснениях и критериях готовности используй букву `ё` с точками там, где она нужна; не заменяй её на `е`.
- В пояснениях и примерах не злоупотребляй списками: максимум три пункта по умолчанию. Более длинные списки допустимы для этапов, правил, проверок или критериев готовности, когда полный перечень действительно нужен.

## Обучающий разбор после практики

После завершения практического этапа разработки, настройки, проверки или деплоя всегда добавляй отдельный Markdown-цитатный блок, начинающийся с `> **💡`, с коротким объяснением одной идеи, которая действительно применена в этой работе: практики безопасности, архитектурного паттерна, подхода к тестированию, Git-приёма или другого полезного принципа. Сохраняй символ `>` перед каждой строкой блока, чтобы интерфейс показывал вертикальную линию слева.

- Перед итогом этапа добавляй отдельную короткую строку прогресса в формате `Этап N/M завершён`, где `N` — число завершённых этапов, а `M` — согласованное общее число этапов проекта. Следом в одном предложении называй следующий этап.

- Объясняй, что это такое, где это применено в текущем проекте и зачем это нужно.
- При первом упоминании технического термина добавляй короткую расшифровку в скобках.
- Держи разбор в пределах 5–7 предложений, разбивай его на небольшие абзацы по 1–3 предложения и не превращай отчёт о работе в общий урок.
- Объясняй один конкретный механизм из текущего этапа по порядку: откуда берутся важные данные, как они передаются и где используются.
- Не повторяй одну идею без новой причины; выбирай следующий разбор по актуальному этапу.
